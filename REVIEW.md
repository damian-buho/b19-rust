# b19/rust Code Review

## Summary

b19/rust is a well-structured Docker base image that installs the Rust toolchain from upstream tarballs with per-arch SHA-512 verification, bundles sccache for compile caching, and provides a sophisticated per-arch RUSTFLAGS probing system. The image follows the b19 `.container/` stage-first layout and m6e makefile conventions closely, with only minor deviations. The overall quality is high -- the declarative deps scheme, the `install-from-cargo` tool, and the flag-probing mechanism are thoughtful designs that downstream images can build on cleanly.

## Architecture

The image is a single-stage `FROM b19/ubuntu` build (named `b19-rust`) with two build-stage invocations:

1. **Root stage (`base`)**: Installs `build-essential` + `pkg-config` via APT, downloads and installs the Rust toolchain from `static.rust-lang.org`, and installs `sccache` from GitHub releases. Both downloads use `b19-resolve-dep` + `b19-fetch` with pinned versions and SHA-512 hashes.

2. **User stage (`user`)**: Runs `install-from-cargo` to install packages declared in `/deps/cargo.txt` (if present).

A secondary set of hooks under `build.d/compile-rust/` is provided for downstream images that `FROM b19/rust` and need to compile Rust code. The pre-hook sources `setup-build`, which probes RUSTFLAGS and configures sccache. The post-hooks install cargo packages and show cache stats.

**Key files:**

- `Dockerfile` -- single-stage build, two `build-stage` calls
- `.container/base/deps/rust/` -- version, per-arch URLs and hashes for Rust
- `.container/base/deps/sccache/` -- version, per-arch URLs and hashes for sccache
- `.container/base/tools.d/setup-build` -- CPU job calculation + RUSTFLAGS probing + sccache activation
- `.container/base/tools.d/install-from-cargo` -- declarative `cargo install` from `/deps/cargo.txt`
- `.container/base/flags/.rustflags/{amd64,arm64}/flags.d/` -- per-arch compiler flags (probed at build time)
- `.makefile/project/10-dependencies.mk` -- auto-generated fetch/hash prerequisite targets

## Strengths

**Declarative dependency scheme.** Every external download (Rust, sccache) has a `.version`, per-arch `.url`, and per-arch `.hash` file under `.container/base/deps/`. The `10-dependencies.mk` makefile fragment (auto-generated by m6e's `generate-deps.sh`) wires these into make prerequisites so `make fetch` pre-downloads everything and `make build` verifies hashes. This is clean, auditable, and automatable.

**Per-arch RUSTFLAGS probing with graceful degradation.** The `setup-build` tool (`tools.d/setup-build`, lines 25-56) reads flag files from `.rustflags/{arch}/flags.d/*.txt`, pipes them through `decomment`, then probes each one individually against a trivial `fn main() {}` program. Only flags accepted by the installed `rustc` are exported. This makes the image portable across VMs, emulators, and heterogeneous hardware without hard-crashing on unsupported ISA extensions. The decision to list individual x86-64-v3 features instead of using `-C target-cpu=x86-64-v3` is the right call.

**Compile cache architecture.** sccache is integrated at multiple levels: installed in the root stage, activated per-compile-stage in `setup-build` (line 60-82), and has its stats logged after each compile stage via `900-show-cache-stats.i.sh`. The Dockerfile uses `--mount=type=cache` for `${B19_COMPILE_CACHE_PATH}` so the cache persists across builds without entering image layers. Redis backend support is built in via `B19_COMPILE_CACHE_REDIS`. The `ccache` case is explicitly handled with a warning that ccache does not support Rust.

**Clean Dockerfile.** The Dockerfile is 66 lines, fully declarative, with no inline scripts. Every `RUN` pairs with a single `build-stage` call. ARG re-declarations after `FROM` are complete. The `--mount=type=bind,from=fetch` pattern connects to the m6e build system's `--build-context fetch=.fetch`. BuildKit cache mounts for APT, Cargo, and compile cache are all present.

**Good i18n coverage.** All user-facing strings in hooks and tools use `_()` and `_p()` gettext macros. Spanish and Ukrainian translations are provided with plural forms. The POT file is up to date with source references.

**Downstream-oriented tooling.** The `install-from-cargo` tool and the `compile-rust` stage hooks are designed for child images, not this image itself. The `scaffold/Dockerfile.template` shows exactly how to consume `b19/rust` as a builder. The `scaffold/stack.conf` declares `STACK_COMPILE_STAGE=compile-rust` and `STACK_EXTENSIONS=rust`, which the scaffolding system uses to generate new projects.

**Test coverage.** Three post-build tests verify the installed toolchain: `0300-apt-versions.sh` checks gcc/make/pkg-config, `1100-rust-version.sh` validates the exact Rust version against the pinned deps file, and `1200-cargo-version.sh` confirms cargo is available.

## Surprises

**`set -e` in tools.d scripts.** Both `tools.d/setup-build` (line 3) and `tools.d/install-from-cargo` (line 3) contain `set -e`. This is surprising because `setup-build` is sourced by its hook (`. setup-build` at `100-setup-build.i.sh` line 3), and the global CLAUDE.md shell safety model says hooks inherit `set -eo pipefail` from `build-stage` and must not add their own. However, `tools.d/` scripts are not hooks -- they are standalone utilities called from hooks. Since `setup-build` is sourced (`. setup-build`), its `set -e` is technically redundant (already inherited), but not harmful. `install-from-cargo` is executed (not sourced), so its `set -e` is correct. This is a borderline inconsistency but not a bug.

**Rust version test uses inverted logic.** The test at `test.d/1100-rust-version.sh` line 6 uses `[ "${EXPECTED}" != "${ACTUAL}" ] && exit 1 || exit 0`. This reads as "if they differ, fail; otherwise pass" which is correct, but the pattern `[ A != B ] && exit 1 || exit 0` is fragile -- if `exit 1` somehow failed (which it cannot in practice), the `|| exit 0` would mask it. The idiomatic form would be `[ "${EXPECTED}" = "${ACTUAL}" ]`. This is a style concern, not a functional bug.

**Missing lineage hook.** `FEATURES.md` (lines 88-93) documents a `990-write-lineage.sh` user post-hook that records the Rust version into the image's lineage file. This file does not exist anywhere in `.container/`. Either the feature was removed without updating the docs, or it is inherited from the parent `b19/ubuntu` image and the docs are misleading about where it lives.

**`_p()` used for non-plural format.** The `900-show-cache-stats.i.sh` line 4 uses `_p "stats: %s"` but this is a simple substitution, not a plural form. The `_()` macro would be more appropriate. The `_p` macro is meant for strings with plural variants (e.g., "1 file" vs "2 files").

**POT file references outdated paths.** The `.pot` file at `.container/base/locale/rust.pot` references paths like `.docker/build.d/install-from-cargo:19` and `.docker/build.d/base/post/500-install-rust.sh:29`. These paths use the old `.docker/` prefix from before the migration to `.container/` (commit `e56f712`). The `.po` files have the same stale references. This is cosmetic -- gettext resolves strings by msgid, not by source path -- but it indicates the POT file was not regenerated after the layout migration.

**ccache case handled twice.** The `ccache` case appears in both `050-install-compile-cache.sh` (base stage, lines 8-10) and `setup-build` (compile stage, lines 78-81). The install hook logs a warning and returns; the setup hook also logs a warning and unsets `RUSTC_WRAPPER`. This is defensive rather than redundant -- the install hook prevents sccache installation when ccache is requested, and setup-build handles the case where someone sets `B19_COMPILE_CACHE=ccache` without going through the base install. Still, the double handling suggests the two stages could share a validation function.

## Issues

### 1. Test script missing `set -eo pipefail` (convention deviation)

**File:** `.container/user/test.d/1100-rust-version.sh`

Per the global shell safety model, `test.d/*.sh` scripts are "subprocess (executed)" and "**must set individually**". This test has no `set -e` or `set -eo pipefail`. If any command before the final comparison failed silently, the test could report a false pass.

Additionally, line 4 uses `grep -oP` (Perl regex), which is GNU-specific. This works on Ubuntu but is worth noting.

### 2. Test script missing `set -eo pipefail` (convention deviation)

**File:** `.container/user/test.d/1200-cargo-version.sh`

Same issue. No `set -e`. A failing `cargo --version` would produce empty output and exit non-zero, but since `set -e` is not set, the script would still exit 0 (success) from the last command's perspective. Actually, `cargo --version` is the only command, so it would propagate the exit code. But if the test were extended later, the lack of `set -e` would be a trap.

### 3. Stale POT/PO source references

**Files:** `.container/base/locale/rust.pot`, `.container/base/locale/es.po`, `.container/base/locale/uk.po`

All source location comments reference `.docker/build.d/...` paths from the pre-migration layout. The actual files now live under `.container/base/build.d/...`. Running `make i18n-extract` would regenerate the POT with correct paths.

### 4. Documented lineage hook does not exist

**File:** `FEATURES.md` lines 88-93

The `990-write-lineage.sh` hook described in FEATURES.md is not present in the codebase. Either it was removed, or it needs to be created. The `read-lineage` make target exists (documented at `docs/MAKEFILE.md:343`) but would have nothing to read without the hook.

### 5. No `CARGO_HOME` cache mount in user stage

**File:** `Dockerfile` lines 58-61

The root stage (line 47) mounts `${CARGO_HOME}` as a BuildKit cache, but the user stage does not. This means if any cargo operations run in the user stage (via `install-from-cargo`), they cannot benefit from the cargo registry cache. The `install-from-cargo` tool does run in the user stage (via `user/build.d/user/post/300-install-from-cargo.i.sh`). For the base image itself this is likely fine (no `cargo.txt` to install), but downstream images that add cargo packages in the user stage will have slower builds due to re-downloading the registry.

### 6. `install-from-cargo` removes deps list after install

**File:** `.container/base/tools.d/install-from-cargo` line 23-24

After installing packages, the script deletes `/deps/cargo.txt` with the comment "We don't need inheritance here." This means the list of installed packages is not visible for debugging at runtime. It also means re-running the user build stage will not have the list, preventing idempotent rebuilds. This is a deliberate design choice (stated in the comment and confirmed by the "We WON'T clean cache" comment on line 28), but it trades debuggability for BuildKit layer optimization.

### 7. `M6E_NAMESPACE` ARG declared but unused in this image

**File:** `Dockerfile` line 22

The `M6E_NAMESPACE` and `M6E_PROJECT` ARGs are declared (lines 22-23) but never referenced in any script or ENV. They are passed by the m6e build system for use by the parent image's tooling (e.g., `b19-load-secrets`, `write-lineage`), so their presence is correct, but worth noting for anyone reading the Dockerfile in isolation.

## Ideas

1. **Add the missing lineage hook.** Create `.container/user/build.d/user/post/990-write-lineage.sh` with `write-lineage "b19/rust" "${M6E_UPSTREAM_VERSION}"` to match the documented behavior in FEATURES.md. Alternatively, if lineage is handled by a hook inherited from b19/ubuntu, update FEATURES.md to clarify that.

2. **Regenerate the POT file.** Run `make i18n-extract` to update source path references from `.docker/` to `.container/`. This will also pick up any new or changed strings since the migration.

3. **Add `set -eo pipefail` to test scripts.** Per convention, `test.d/*.sh` must set their own error handling. Adding `set -eo pipefail` to `1100-rust-version.sh` and `1200-cargo-version.sh` would be consistent and safer for future changes.

4. **Simplify the version test comparison.** In `1100-rust-version.sh`, replace the `[ A != B ] && exit 1 || exit 0` pattern with `[ "${EXPECTED_VERSION}" = "${ACTUAL_VERSION}" ]` for clarity and correctness.

5. **Consider adding `CARGO_HOME` cache mount to the user stage.** This would help downstream images that install cargo packages in the user stage. It would look like `--mount=type=cache,target=${CARGO_HOME},sharing=private,uid=${B19_UID},gid=${B19_GID}` in the user stage `RUN` block.

6. **Extract ccache validation to a shared utility.** The "ccache does not support Rust" warning appears in two places (`050-install-compile-cache.sh` and `setup-build`). A small function in `tools.d/` could centralize this logic and keep the two stages consistent.

7. **Add a `rustfmt --version` test.** The image installs the full Rust toolchain including rustfmt. A `1300-rustfmt-version.sh` test would verify the formatter is available, which is useful since downstream CI images often depend on it.

8. **Consider adding `CARGO_NET_OFFLINE=true` as a conditional ENV.** When `B19_OFFGRID_MODE` is set, setting `CARGO_NET_OFFLINE=true` would prevent cargo from attempting network access, providing clearer error messages in offline builds.
